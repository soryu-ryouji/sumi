# 全文检索设计（FTS5）

## 契约与范围

`POST /api/v1/item/list` 的 `content` 参数（见 [REST API V1](server-rest-api-v1.md)）：

- 检索范围为 **txt / md / epub / docx 的正文**（mobi/azw3/pdf 列后续版本，不支持的格式不命中）
- 查询语法：**短语用双引号，空格为 AND**（如 `content: "黑暗森林" 威慑` = 「黑暗森林」子串 AND 「威慑」子串）
- 与其他过滤参数组合逻辑为 AND

索引落在库外派生缓存 `index.db` 的 FTS5 表中（见 [storage.md](storage.md)「元数据派生缓存」），**两种存储模式共用**，不参与同步、可整体删除、重启自动重建——全文索引是「本机加速」特性，不是权威数据。

## 分词器

### 候选对比

| 方案 | 问题 |
| ---- | ---- |
| unicode61（FTS5 内建） | 连续 CJK 字符被切成**一整个超长 token**（中文无空格），整句无法命中，中文不可用 |
| trigram（FTS5 内建） | 每字进 3 个 trigram，索引膨胀约 3x；查询词不足 3 字符时退化，二字词（中文高频）无法直接走索引 |
| jieba 等词典分词 | 词级索引依赖词典质量；查询词恰好跨词边界时漏召回（「黑暗森林」切成「黑暗/森林」后查「暗森」不命中），需要回退逻辑 |
| **CJK 单字 + 西文词**（选定） | 按字索引 + 短语查询 = 子串精确匹配：中文无空格，字序列邻接即原文连续，任何查询词都不会跨边界漏召回；索引膨胀约 1–3x（FTS5 posting list 的 delta+varint 压缩后），term 数有界（汉字约 2 万 + 西文词表） |

### 选定方案

自定义 FTS5 tokenizer（经 rusqlite `create_tokenizer` 注册为 `sumi_tokenizer`）：

- CJK 表意文字（含扩展 A–G）**逐字成 token**，token 保留原文（区分大小写的西文折叠为小写）
- 西文/数字连续串**成词 token**（`hello`、`iPhone15` 各一个）
- 标点、空白、控制字符为分隔符，不产生 token

查询语义推论：**关键词的分词结果做短语查询（邻接匹配）= 原文子串匹配**。「黑暗森林」分词为 `黑 暗 森 林`，短语查询 `"黑 暗 森 林"` 要求四字按序邻接——即原文出现「黑暗森林」连续子串。中文检索不依赖词典、无漏召回，这是选它的根本原因。

## 查询语法映射

客户端传来的 `content` 字符串映射到 FTS5 查询：

1. 按空白拆为关键词；**双引号内的内容为一个关键词**（允许含空格，西文短语场景），引号剥离
2. 每个关键词经 `sumi_tokenizer` 切分（与建索引同一分词器，口径必然一致）
3. 关键词分词结果重组为 FTS5 **短语查询**（`"黑 暗 森 林"`）；单词 token 直接为 term
4. 多个关键词之间 **AND** 连接
5. 边界：关键词分词后为空（纯标点/空白）→ 忽略该关键词；全部为空 → 不追加全文条件（等价未传）

FTS5 查询串中的特殊字符（`"`、`*`、`NEAR` 等）经 FTS5 字符串字面量规则转义，用户输入不被解释为 FTS5 语法（防注入：查询语法是 sumi 的子集，不是 SQL/FTS 直通）。

## 正文提取与写入管道

- **提取时机**：入库解析时一次解包同出（与封面、书目元数据共用同一次文件打开——首扫并行阶段产出；`refresh_cache` 补缺失模式重派）。提取来源：txt/md 为解码后原文；epub 为 spine 顺序拼接的 XHTML 文本；docx 为 document.xml 文本流
- **表结构**：`fts(item_id UNINDEXED, text)`，`item_id` 列不建倒排、仅作关联（contentless 变体在删除时需重建，不取）；正文文本存入 `text` 列供 token 化
- **生命周期联动**：id 漂移迁移元数据时 FTS 行随迁（delete + insert）；移入回收站保留（回收站可搜索的语义未定义，保守保留）；`trash/clear` 与 `cleanup_index` 摘除时删除对应行；缓存重建全量重写

## 体积与性能特性

- 索引体积与正文文本线性相关，膨胀系数约 1–3x（FTS5 posting list 压缩后）；千本书库为 GB 级，属于「可删可重建的本机缓存」语义，磁盘紧张的用户删掉 `index.db` 即放弃全文检索能力（其余功能不受影响，`content` 查询退化为不命中）
- 查询延迟：倒排求交在万本库规模为毫秒级；`content` 与其他过滤条件（标签/文件夹/阅读状态等）组合时，先在内存索引过滤出候选集，再对候选集做 FTS 命中判定（避免全库 FTS 扫描）
- 高亮/命中定位（snippet）：v1 契约未定义，不实现；后续版本如需增加，经 API 契约扩展（响应加字段），不动存储格式
